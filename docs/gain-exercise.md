# Gain Exercise

**Email Chain Analysis & Auto-Reply System**

## Objective

Integrate with the Gain Email Server (REST API), reconstruct email threads from individual messages, and reply to every unread incoming conversation. The exercise is open-ended — **any programming language is fine**; you also choose the storage layer and project structure. We care about how you decompose the problem and reason about correctness.

**On AI assistance:** using AI tools (Copilot, Cursor, Claude, ChatGPT, etc.) is allowed and expected. That said, you own every line in the final submission — be ready to walk through the design, explain why each piece exists, and modify any of it on the spot. If you can't defend it, don't ship it.

## System Under Test

- **Base URL:** `http://emailsapi.northeurope.cloudapp.azure.com:8009`
- **Swagger:** `/docs`
- **Auth:** none required

### Endpoints

| Method | Path                          | Purpose                                            |
|--------|-------------------------------|----------------------------------------------------|
| GET    | `/emails?start=0&end=50`      | List emails by index range, newest first           |
| GET    | `/emails/{email_id}`          | Fetch a single email by UUID                       |
| POST   | `/emails/send`                | Send a new email; pass `in_reply_to` for replies   |
| PUT    | `/emails/{email_id}/read`     | Mark an email as read / unread                     |
| GET    | `/health`                     | Service health check                               |

Each email carries: `id` (UUID), `subject`, `from_address`, `to_addresses`, `body`, `is_read`, `is_sent`, `email_direction` (*in* | *out*), `in_reply_to`, `created_at`.

## Core Tasks

### 1. Fetch all emails

- Iterate `GET /emails` with a paging window until the response is empty.
- Persist the raw emails into local storage of your choice (SQLite, Postgres, JSONL, in-memory — justify the trade-off).

### 2. Reconstruct threads

An email thread is the transitive closure of `in_reply_to` relationships. The smallest valid thread is a single email with no parent and no children.

- Build a forest where each node is an email and edges follow `child.in_reply_to == parent.id`.
- A *thread* is one connected component (root + all descendants).
- Be defensive: parents may be missing, cycles should be impossible but assert it, and timestamps may tie — break ties deterministically.
- **Persist all threads to a "database"** — a JSON file on disk is enough; SQLite, Postgres, or anything else is fine if you prefer. Pick what you can defend.

### 3. Identify the latest message per thread

- For each thread, the *latest* email is the one with the maximum `created_at`.
- A thread is *actionable* when its latest email is `email_direction == "in"` and `is_read == false`.
- Threads whose latest email is outgoing (you already replied) or already read should be skipped.

### 4. Reply to every actionable thread

For each actionable thread, send a reply via `POST /emails/send` with:

```json
{
  "subject": "Re: <original subject>",
  "from_address": "natalie@somecompany.com",
  "to_addresses": ["<original sender>"],
  "body": "<your reply>",
  "in_reply_to": "<UUID of latest email in thread>"
}
```

- After a successful reply, mark the original email as read via `PUT /emails/{email_id}/read`.
- **Reply body must be generated by an LLM** (Claude, GPT, local model — your choice). The prompt should receive the full thread, not just the last message. Note which model and prompt shape you used in the write-up.
- Make the operation safe to re-run: a second pass should reply to zero threads.

## Bonus: Spam Classification

The mailbox is seeded with messages drawn from a public spam/ham dataset. Build a classifier that labels each stored email as *spam* or *ham*, and use it to filter the auto-reply step so we don't reply to obvious spam.

- Any approach is fair game: keyword heuristics, classical ML (Naive Bayes, logistic regression on TF-IDF), or an LLM zero-shot prompt. Pick what you can defend.
- Persist the predicted label and a confidence score next to each email in your storage.
- Report a confusion matrix or precision/recall on a held-out slice if you train a model.
- Skip auto-replying to anything classified spam; surface the count in your run summary.

## Technical Requirements

- Pagination handled correctly until the dataset is exhausted.
- Clear separation between API client, thread builder, reply policy, and (optional) classifier.
- Configuration via environment variables — no hard-coded secrets.
- A single command to run end-to-end (e.g. `make run` or `python -m app`).
- **Suggestion:** if you go with Python, use `uv` for dependency management — it's fast and gives us a one-command setup.

## Deliverables

- A short write-up (half a page is plenty) covering: storage choice, threading algorithm, and what you would do with another day.
- A run log or CLI output showing: emails fetched, threads built, replies sent, spam filtered.

## How We Evaluate

- **Correctness:** threads reconstructed accurately; only the right emails are replied to; replies are idempotent.
- **Reply quality:** LLM-generated replies are coherent, on-topic, and grounded in the thread context.
- **Code quality:** readable structure, named abstractions, tests where they earn their keep.
- **Judgement:** the trade-offs you call out in the write-up matter as much as the code.
